## P1 封面【10s｜累计 0:10】

各位老师好，我们是第 4 组，答辩项目是智能会议室管理系统 V1.0。我用 5 分钟讲三件事：需求怎么定、系统怎么设计、验证做到了什么程度。

## P2 需求基线【40s｜累计 0:50】

先说需求从哪来。我们的需求基线是需求清单 V1.1：20 条功能需求、15 条非功能需求，每条非功能都写明了验证方式；用例规约写了 6 份，覆盖普通用户登录、提交预约、查看修改、取消，和管理员管房间、处理预约，6 份规约覆盖了全部 20 条功能和所有异常分支。

我们特别在意范围控制：9 项明确不做的东西——人脸识别、物联网、3D 场景这些——写进了文档，但坚决不实现、不画进图里，避免做成"综合管理平台"式的模糊口径。我们的验收标准是：每条需求都能被一个用例和一次测试命中。

## P3 半开区间规则【30s｜累计 1:20】

需求分析里我们最较真的是冲突判定规则。判定式是：新时段开始早于已有结束、且新时段结束晚于已有开始。注意两个不等号都是严格小于——这决定了首尾相接不算冲突：10 到 11 点被订了，11 到 12 点照样能订，这是真实使用中最常见的连续预约，判错一次就是缺陷。部分重叠则直接拒绝。这条口径由需求评审 R-04 定下，需求清单、用例规约、接口文档、SQL 四处写的都是同一句话。

## P4 概要设计【40s｜累计 2:00】

概要设计选了前后端分离加 MySQL：前端 Vue 3 加 TypeScript，后端 Spring Boot 3 REST 加 MyBatis，数据库 MySQL 8 InnoDB，单机三个进程，5173、8080、3306。后端分四层，前端六个模块，每个模块都挂得上需求编号；对外 14 条 REST 接口，一套统一响应封装，JWT 鉴权，角色校验放在服务端而不是前端隐藏菜单。两条硬约束：前端零 JDBC 不直连数据库，跨域只由后端统一放行。

## P5 数据库设计【40s｜累计 2:40】

数据库 4 张表：用户、会议室、预约、操作日志。有四个设计决策想说一下理由：一，外键全用 RESTRICT，有预约的房间删不掉，业务数据不会静默丢；二，预约表冗余了一个日期列，让按日占用聚合走索引，用 CHECK 约束保证它和开始时间同一天；三，不写定时器改状态，状态在读写时按时间推导加一次校正 SQL，单机部署不留后台任务；四，操作日志不级联删除，审计记录独立留存。

## P6 提交预约事务【40s｜累计 3:20】

详细设计讲一个核心流程：提交预约在同一个事务里做五步——参数校验、锁会议室行、冲突查询、写入、提交。右边就是冲突 SQL 和行锁语句。为什么先锁行再查？因为只查不锁的话，两个事务可能同时查到"无冲突"再各自插入；行锁把同一会议室的判定串行化，后到的事务能看到已提交记录，自然拿到 409。

## P7 并发验证【35s｜累计 3:55】

这套设计我们用真并发验证过：50 个线程用 Barrier 同时起跑，抢同一房间同一时段，结果 1 条成功、49 条明确返回 409 和占用时段，没有超时、没有静默失败、没有第二条有效预约。另外顺手修了一个性能点：超时预约校正 SQL 原来是全表扫描 3632 微秒，加上日期条件走索引后 253 微秒，快了约 14 倍，等价性由 CHECK 约束保证。

## P8 验证总览【25s｜累计 4:20】

整体验证：43 项接口回归全通过、6 个功能异常用例全通过、16 组 SQL 注入载荷全部无效。同时我们如实标出两项短板：业务失败目前统一回 HTTP 200，和任务书的 409 判据不一致，已列入预答辩前修复；浏览器兼容和干净机部署两项复现由组内同学补测。

## P9 结论【20s｜累计 4:40】

结论三句话：20 条功能全部有接口、页面、测试对应；冲突口径从需求一路对到 SQL；并发只出一条有效预约。局限和下一步都列在页面上。这个系统的价值不在功能多少，而在每条规则都能从需求编号一路查到测试证据。

## 可能被问的问题与简答

1. **为什么业务失败回 HTTP 200？**（最可能被问）
   答：当前统一响应封装把业务码放在 body 的 code 里，前端按 code 分支处理。已知与任务书 409 判据不一致，改动方案是异常处理器返回对应状态码、前端同步适配，已排进预答辩前，改完会重跑 43 项回归和 50 并发。
2. **50 并发怎么保证真的同时？**
   答：Java CountDownLatch/Barrier 让 50 个线程都就绪后同时放行；跑完直接查库里的记录数和状态分布，不是只看响应。
3. **首尾相接如果允许，两个人的会议怎么衔接？**
   答：会议室预约的占用边界是 [start, end)，前一场的结束时刻就是下一场的开始时刻，物理上不冲突；这也是医院、教室预约系统的通用口径。
4. **如果只给 3 分钟怎么办？** 保留 P1、P3、P6、P7、P8 五页，砍需求基线和结论页。
5. **数据量再大会怎样？**
   答：冲突查询走 (room_id, reserve_date, start_time) 组合索引，1000 条量级实测 253µs；万级压测已列入下一步。
