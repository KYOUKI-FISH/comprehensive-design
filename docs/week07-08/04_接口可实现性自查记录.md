#### #11 会议室管理 `GET·POST·PUT·DELETE /api/admin/rooms` —— ⚠️ 可写但有歧义

草案表把 4 个方法合并成一行。**按方法拆开，签名如下**：

```java
// com.meetingroom.controller.AdminController（第 9 周新建）
@GetMapping("/rooms")
public ApiResponse<List<RoomVO>> listRooms(
    @RequestParam(required = false) String status,
    @RequestParam(required = false) String location)

@PostMapping("/rooms")
public ApiResponse<RoomVO> createRoom(@RequestBody RoomRequest request)

@PutMapping("/rooms/{id}")
public ApiResponse<RoomVO> updateRoom(
    @PathVariable Long id,
    @RequestBody RoomRequest request)

@DeleteMapping("/rooms/{id}")
public ApiResponse<Void> deleteRoom(@PathVariable Long id)
```

**入参**（`RoomRequest`）：

| 字段 | 类型 | 必填 | 备注 |
|------|------|------|------|
| `name` | `String` | ✔ | **唯一**，FR-03 |
| `location` | `String` | ✔ | 位置 |
| `capacity` | `Integer` | ✔ | CHECK `> 0` |
| `equipment` | `String` | ✘ | 默认 `''` |
| `remark` | `String` | ✘ | |
| `status` | `String` | ✘ | `ENABLED`／`DISABLED`，**PUT 时传即停用** |

**失败**：`403`／`400`「会议室名称与位置不能为空」／**`409`「同名会议室已存在」**（唯一键 `uk_room_name` 冲突）／`404`／**`409`「该会议室存在预约记录，无法删除」**（`ON DELETE RESTRICT`）
**独立推导出的关键点**：
- **`PUT` 同时承载启用/停用**——传 `status=DISABLED` 即停用，**不需要另开一个接口**（与既有 `meeting_room.status` 列一致）
- **`DELETE` 的 409 是数据库直接拒绝的**（外键 RESTRICT），不是业务判断。异常信息应转成中文业务提示，不把 SQL 原文抛给用户。

> ⚠️ **歧义点**：草案表写 `GET·POST·PUT·DELETE /api/admin/rooms`，但 **`PUT` 与 `DELETE` 需要路径参数 `{id}`**，实际路径是 `/api/admin/rooms/{id}`，与 `POST /api/admin/rooms` 不是同一路径。**建议在第 8 周定稿表里拆成 4 行写清**，否则第 9 周可能写错。

#### #12 用户管理 `GET·POST·PUT /api/admin/users` —— ⚠️ 可写但有歧义

```java
// com.meetingroom.controller.AdminController（第 9 周新建）
@GetMapping("/users")
public ApiResponse<List<UserVO>> listUsers(
    @RequestParam(required = false) String status,
    @RequestParam(required = false) String role)

@PostMapping("/users")
public ApiResponse<UserVO> createUser(@RequestBody UserCreateRequest request)

@PutMapping("/users/{id}")
public ApiResponse<UserVO> updateUser(
    @PathVariable Long id,
    @RequestBody UserUpdateRequest request)
```

**入参**（`UserCreateRequest`）：`username`✔、`password`✔、`realName`✔、`phone`✘、`role`✘（默认 `USER`）
**入参**（`UserUpdateRequest`）：`status`✘、`realName`✘、`phone`✘
**出参**：`UserVO`，**绝不含 `password` 字段**
**失败**：`403`／`400`「账号已存在」／`400`「密码长度不足 6 位」／`404`「用户不存在」／`400`「不能停用当前登录的管理员账号」
**独立推导出的关键点**：

## 3. ★ 发现冲突 1：统一返回体的 `code` 语义，设计文档与既有代码不一致

### 3.1 现象

| 来源 | 说法 |
|------|------|
| 《01_系统设计说明书》§3.1 统一约定 | `code = 0` 为成功，非 0 为业务错误 |
| 《02_数据库与接口设计》§3.1 统一约定 | 同上，`code = 0` |
| **既有代码 `ApiResponse.java`** | **`public static final int CODE_OK = 200;`** —— 成功是 **200** |
| **既有代码 `BusinessException`** | 错误码用 `400`／`401`／`403`／`404`／`500` |
| **既有前端 `api/http.ts`** | **`if (body.code !== 200) { throw new Error(...) }`** —— 判 200 |
| **既有前端 `types/api.ts`** | `/** 200=成功；400 入参不合法；401 账号或密码错误… */` |

### 3.2 为什么这是**必须现在解决**的问题

前端 `request<T>()` 是全站唯一的请求入口，它**硬编码判 `code !== 200`**。

如果第 9 周后端按设计文档返回 `code: 0`：
- 前端 `body.code !== 200` 成立 → **抛 `Error`**
- **每一个成功请求都会被前端当成失败** → 登录都登不进去
- 而且**前端 `http.ts` 一行都不用改**（它是既有代码，改它会动第 6 周已联调通过的链路）

反过来说：**既有代码是对的，设计文档写错了。** 既有 `ApiResponse` 的类注释已经把这条约定固化下来了——

> 约定：业务失败也返回 HTTP 200，靠 `code` 区分结果，避免前端在 HTTP 状态码与业务码之间来回判断。

这条约定**自洽且已落地**，而设计文档的 `code=0` 是一处笔误级别的不一致。

### 3.3 裁决与处理结果：✅ **已修复（2026-10-21）**

**改设计文档，不改代码。** 两份文档的表述已统一改为：

> 统一响应体 `{ "code": 200, "message": "ok", "data": ... }`；
> **`code = 200` 表示成功**（与既有 `ApiResponse.CODE_OK` 一致），非 200 为业务错误（400／401／403／404／500），**业务失败也返回 HTTP 200**，由前端按 `code` 判定。

**实际改动**（3 处，2026-10-21）：

| 文件 | 位置 | 改动 |
|------|------|------|
| `01_系统设计说明书.md` | §4.2 #2 登出 | `code=0` → `code=200`（`ApiResponse.success()`，data 为 null） |
| `02_数据库与接口设计.md` | §3.1 统一约定 | 整行改写，补明"与既有 `ApiResponse.CODE_OK = 200`、前端 `http.ts` 的 `body.code !== 200` 判定完全一致" |
| `02_数据库与接口设计.md` | §3.4 #2 登出、#8 取消 | `code = 0` → `code = 200` |

**为什么是"改文档"而不是"改代码"**：
1. 既有代码已跑通并联调通过（第 6 周实测 + 李牧远 10-13 另一台机器独立复现）；
2. 改前端 `http.ts` 的判定会动到第 6 周已验证的链路，风险不对称；
3. `code=200` 与 HTTP 语义码对齐，**比 `code=0` 更好读**——前端同学不用记"0 才是成功"这种反直觉约定。

**影响面**：**接口路径、方法、入参出参结构均不受影响**，属《01_系统设计说明书》§4.4「接口边界变更记录」里的**不改动**范畴。

### 5.3 ★ 调用侧发现的第 3 个问题：`409` 的 `occupiedSlots` 拿不到

**问题**：设计要求 `409` 响应体里带 `data.occupiedSlots`（被占用时段），让前端能展示"当日已占用"。

但既有 `http.ts` 的 `request<T>()` 逻辑是：

```typescript
if (body.code !== 200) {
  throw new Error(body.message || '请求失败')   // ← 只带 message，data 被丢弃
}
```

**`data` 在抛异常时直接丢掉了**，前端拿不到 `occupiedSlots`，只能看到一句「该会议室在此时间段已被占用」。

**这是既有代码与新需求的真实冲突**，且**必须解决**——FR-10 要求冲突时返回被占用时段，前端要能展示。

**三个方案**：

| 方案 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| **A（推荐）** | `http.ts` 的 `Error` 上挂一个 `data` 字段：<br>`const err = new Error(msg) as Error & { data?: T }`<br>`err.data = body.data; throw err` | 改动小（3 行），**不破坏既有调用方**（既有 `catch` 只读 `.message`，多挂一个字段无害） | 要动 `http.ts`——**但这是新增字段不是改判定**，风险低 |
| B | 冲突时后端把占用时段拼进 `message` 文案里 | 后端零改动 | 文案拼接、无法结构化展示、难写单测 |
| C | 前端不用统一封装，冲突单独走 axios | 不动 `http.ts` | 破坏"统一入口"设计，14 条接口写法不统一 |

### 5.4 处置决定（2026-10-21，组长决定）

**决定：本次不改 `http.ts`，只把问题写进文档，留到第 9 周写 `BookingView` 之前处理。**
