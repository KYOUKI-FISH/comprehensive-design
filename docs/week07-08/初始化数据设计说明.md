## 一、设计目标

初始化数据不是"随便塞几条"，而是**每一条都要能验证一个需求点**。验收时老师随手查一条数据，就该能说出它在证明什么。

四条设计目标：

| 目标 | 做法 |
|------|------|
| **可登录** | 内置 3 个账号，管理员 + 2 个普通用户，**普通用户分属不同人**，才能演示"我的预约"的数据隔离（FR-11） |
| **可验证停用过滤** | 3 间会议室里放 **1 间 `DISABLED`**，查询页必须查不到它（FR-06） |
| **可复现冲突** | 预约数据里放**一组重叠**和**一组首尾相接**，前者判冲突、后者不判（FR-09／FR-10） |
| **可验证状态流转** | 覆盖 `PENDING`／`FINISHED`／`CANCELLED` 三态，证明四态枚举不是摆设（NF-08） |

## 四、如何复现冲突（演示时照着做）

> 这是本份说明最实用的一节。**课堂演示按下面三步走，冲突判定会当场可见。**

### 步骤 1：造一个冲突（应被拒绝）

1. 用 `user1` 登录 → 会议室列表 → 选 **A101**；
2. 预约日期填 **`2026-11-02`**，时段填 **`10:30`–`11:30`**；
3. 提交 → **应提示「该会议室在此时间段已被占用」**。

**为什么冲突**：A101 已有 `09:00-11:00`（#1）与 `10:00-12:00`（#2）。
`10:30` 落在 09:00-11:00 内 → 冲突；落在 10:00-12:00 内 → 也冲突。**命中 2 条。**

> 判定式（半开区间 `[start, end)`）：
> ```sql
> WHERE room_id = 1 AND reserve_date = '2026-11-02' AND status <> 'CANCELLED'
>   AND start_time < '2026-11-02 11:30:00'   -- 新开始 < 旧结束
>   AND end_time   > '2026-11-02 10:30:00'   -- 新结束 > 旧开始
> ```

### 步骤 2：造一个首尾相接（应被放行）

1. 仍用 `user1`，但改选 **A202**；
2. 日期 `2026-11-02`，时段填 **`11:00`–`12:00`**；
3. 提交 → **应成功**。

**为什么不算冲突**：A202 已有 `09:00-10:00`（#3）与 `10:00-11:00`（#4）。新建的 `11:00-12:00` 正好接在 #4 的**尾巴**后面——`start_time(11:00) < end_time(10:00)` 不成立，**不重叠**。

> ★ 这是 **FR-09「首尾相接不算冲突」**的现场验证。判定式里必须是**严格不等**（`<` / `>`），改成 `<=` 就会把 11:00 这个边界判成冲突。

### 步骤 3：验证取消后时段释放

1. `user1` 登录 → 我的预约 → 找到 #5（14:00–15:00，状态已取消）；
2. 或直接在 A101 上提交 `14:00`–`15:00` → **应成功**（#5 已 `CANCELLED`，不参与占用判定）。

## 五、脚本自带的自动验证

`schema.sql` 末尾带 **5 段自检查询**，执行脚本时会自动打印，**演示时不必手工敲**：

| 段 | 校验内容 | 期望输出 |
|----|---------|---------|
| ① | 已建表清单 | 4 张表（`user`／`meeting_room`／`reservation`／`operation_log`） |
| ② | 各表记录数 | user 3／meeting_room 3／reservation 7／operation_log 1 |
| ③ | 预约状态分布 | `PENDING` 5／`FINISHED` 1／`CANCELLED` 1（`ONGOING` 未造数据） |
| ④ | **冲突组实证** | 新预约 10:30-11:30 → **命中 2 条**；14:00-15:00（原记录已取消）→ **命中 0 条** |
| ⑤ | **首尾相接实证** | 11:00-12:00 → **0 条**；08:00-09:00 → **0 条**；09:30-10:30 → **2 条** |

> ★ **第 ④⑤ 段是本组设计的核心证明**：三组结果必须**同时成立**。全是 0 = 判定式写错；第 2、3 行大于 0 = 用了 `<=` 而非 `<`，**首尾相接被误判成冲突**。

## 六、口径与注意事项

| # | 事项 | 说明 |
|---|------|------|
| 1 | **口令不入库** | 脚本里只有 BCrypt 摘要；明文只在根 `README.md`（NF-05） |
| 2 | **无哈希串外泄** | 文档与截图均不出现 BCrypt 密文 |

| 4 | **可重复执行** | 脚本先 `DROP` 再重建，**有破坏性**，勿在有真实数据的环境执行 |
| 5 | **测试库隔离** | 回归测试的破坏性写入只在测试库做，不污染演示库（NF-15） |
| 6 | **预约编号规则** | `MR` + yyyyMMdd + 3 位序号，如 `MR20261102001`；由业务层生成（第 9 周实现） |
| 7 | **两版脚本同源** | `schema.sql` 与 `database/` 拆分版 **4 张表 DDL 逐字符一致** |
