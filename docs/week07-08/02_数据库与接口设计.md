实体与关系口径（供画图直接用，与 §二 表结构、`schema.sql` 严格一致）：

| 预约 `reservation` | `id` | `booking_no`（唯一）、`booking_date`、`start_time`、`end_time`、`topic`、`attendee_count`、`contact`、`purpose`、`status`（0/1/2/3 四态）、`cancel_reason` | N : 1 `user`、N : 1 `meeting_room` |
| 操作日志 `operation_log` | `id` | `operator_id`、`operator_username`（冗余快照）、`operation_type`、`target_type`、`target_id`、`before_data`（JSON）、`after_data`（JSON）、`operated_at` | N : 1 `user` |

**为什么是 4 张表而不是 3 张**：NF-14（可审计性）是需求清单 V1.1 的**必须完成项**且带验证方式（查系统操作日志、字段完整、普通用户访问被拒）。ER 图与脚本漏了它就与需求清单不同源，故增补 `operation_log` 表，对应接口清单第 13 条 `GET /api/admin/logs`。这是对 NF-14 的补齐，不是范围外扩张。

**为什么没有 role 表、没有其他关联表**：本组只有 USER／ADMIN 两种固定角色，FR-01～FR-20 中无"角色管理"功能。按"需求清单里没有的功能不要画进设计"的硬要求，`role` 以枚举列承载，**不建 role 表**，也不建 `user_role` 等关联表。

## 二、物理表结构（4 张表，逐字段）

> 口径：字段名／类型／可空／默认值／约束／说明，与 `schema.sql` 逐字段一致。
> 时间字段一律 `DATETIME`（见 §五 说明 1）；状态取值逐个列清（见 §五）。

### 2.1 `user`　用户表

支撑需求：FR-01（登录）、FR-02（角色区分）、FR-14（管理用户）、NF-05（密码不得明文）

| 字段 | 类型 | 可空 | 默认值 | 约束 | 说明 |
|------|------|------|--------|------|------|
| `id` | BIGINT UNSIGNED | 否 | 自增 | 主键 | 用户 ID，对外不暴露，接口层用 |
| `username` | VARCHAR(50) | 否 | — | 唯一 `uk_user_username` | 登录账号；管理员建号时重名报 `409 账号已存在`（FR-14） |
| `password` | VARCHAR(100) | 否 | — | — | **BCrypt 摘要**（cost=10，固定 60 字符）。禁止存明文（NF-05）；校验必须用 `BCryptPasswordEncoder.matches()` |
| `real_name` | VARCHAR(50) | 否 | — | — | 姓名，用于展示与操作人留痕 |
| `role` | VARCHAR(20) | 否 | `'USER'` | CHECK ∈ ('USER','ADMIN') | 角色；FR-02 权限隔离的依据。**不建 role 表** |
| `phone` | VARCHAR(20) | 是 | NULL | — | 联系电话；演示数据不用真实手机号（NF-06） |
| `status` | VARCHAR(20) | 否 | `'ACTIVE'` | CHECK ∈ ('ACTIVE','DISABLED') | 账号状态；DISABLED 后不能登录（FR-14、NF-05） |
| `created_at` | DATETIME | 否 | 当前时间 | — | 创建时间 |
| `updated_at` | DATETIME | 否 | 当前时间 | `ON UPDATE` 自动刷新 | 最后更新时间 |

索引：主键 `id`；唯一 `username`；普通索引 `role`、`status`（管理端按角色/状态筛选用，FR-14）。

### 2.2 `meeting_room`　会议室表

支撑需求：FR-03（会议室管理）、FR-04（启停）、FR-05（条件查询）、FR-06（显示可用状态）

| 字段 | 类型 | 可空 | 默认值 | 约束 | 说明 |
|------|------|------|--------|------|------|
| `id` | BIGINT UNSIGNED | 否 | 自增 | 主键 | 会议室 ID |
| `name` | VARCHAR(100) | 否 | — | — | 名称，仅展示；**唯一性不由 name 保证** |
| `building` | VARCHAR(50) | 否 | — | 联合唯一 `uk_room_building_no` | 楼栋；与房间号共同支撑 FR-03"相同楼栋和房间号拒绝重复新增" |
| `room_no` | VARCHAR(20) | 否 | — | 联合唯一 `uk_room_building_no` | 房间号 |
| `capacity` | INT UNSIGNED | 否 | — | CHECK `capacity > 0` | 容纳人数；FR-05 按容量筛选的比较字段 |
| `equipment` | VARCHAR(255) | 否 | `''` | — | 设备描述，仅展示 |
| `purpose` | VARCHAR(100) | 否 | `''` | — | 会议室用途说明，仅展示 |
| `status` | VARCHAR(20) | 否 | `'ENABLED'` | CHECK ∈ ('ENABLED','DISABLED') | 启停状态；停用后**已有预约保留**，但不作为新预约选项（FR-04、FR-06） |
| `remark` | VARCHAR(255) | 是 | NULL | — | 备注 |
| `created_at` | DATETIME | 否 | 当前时间 | — | 创建时间 |
| `updated_at` | DATETIME | 否 | 当前时间 | `ON UPDATE` 自动刷新 | 最后更新时间 |

索引：主键 `id`；联合唯一 `(building, room_no)`；普通索引 `status`、`capacity`、`building`（FR-05 三类筛选各走一个索引前缀）。

### 2.3 `reservation`　预约记录表（核心表）

支撑需求：FR-07～FR-13、FR-15、FR-16、FR-18、NF-07（并发不超订）、NF-08（状态流转）

| 字段 | 类型 | 可空 | 默认值 | 约束 | 说明 |
|------|------|------|--------|------|------|
| `id` | BIGINT UNSIGNED | 否 | 自增 | 主键 | 预约主键；对外不暴露，对外用 `booking_no` |
| `booking_no` | VARCHAR(32) | 否 | — | 唯一 `uk_reservation_booking_no` | 预约编号，对外展示（FR-07）。规则：`BK + yyyyMMdd + 4位序号`（如 BK202611020001），业务层生成（第 9 周） |
| `user_id` | BIGINT UNSIGNED | 否 | — | 外键 → `user(id)` **ON DELETE RESTRICT** | 预约人（FR-11 归属）。删用户被数据库直接拒绝，不因删用户毁掉预约记录 |
| `room_id` | BIGINT UNSIGNED | 否 | — | 外键 → `meeting_room(id)` **ON DELETE RESTRICT** | 会议室（FR-03 删除保护）。**有预约的会议室删不掉**——"删掉一间会议室会不会影响已有预约"的答案就落在这条外键上 |
| `booking_date` | DATE | 否 | — | CHECK `= DATE(start_time)` | 预约日期，恒等于开始时间的日期部分（CHECK 保证不漂移）；用于按日查询、占用日历（FR-17）与按日聚合（FR-20） |
| `start_time` | DATETIME | 否 | — | CHECK 参与 | **开始时间，含本时刻（半开区间左闭）**；不得早于当前时间（FR-08） |
| `end_time` | DATETIME | 否 | — | CHECK `> start_time` | **结束时间，不含本时刻（半开区间右开）**；占用区间为 `[start_time, end_time)` |
| `topic` | VARCHAR(100) | 否 | — | — | 会议主题，必填（FR-07） |
| `attendee_count` | INT UNSIGNED | 否 | — | CHECK `> 0` | 参会人数，必填（FR-07） |
| `contact` | VARCHAR(50) | 否 | — | — | 联系人，必填（FR-07） |
| `purpose` | VARCHAR(255) | 是 | NULL | — | 用途补充说明，选填（FR-07 只要求主题/人数/联系人/起止时间必填） |
| `status` | TINYINT | 否 | `0` | CHECK ∈ (0,1,2,3) | **0 待开始 / 1 进行中 / 2 已结束 / 3 已取消**（NF-08 四态；不用任务书示例的三态，见 §五 说明 3） |
| `cancel_reason` | VARCHAR(200) | 是 | NULL | — | 取消原因；**管理员强制取消时必填**（FR-16），用户自行取消可留空 |
| `created_at` | DATETIME | 否 | 当前时间 | — | 创建时间 |
| `updated_at` | DATETIME | 否 | 当前时间 | `ON UPDATE` 自动刷新 | 最后更新时间 |

索引：主键 `id`；唯一 `booking_no`；联合索引 `idx_reservation_room_time (room_id, booking_date, start_time, end_time)`（§三）；`idx_reservation_user_date (user_id, booking_date)`（"我的预约"按日期查，FR-11）；`idx_reservation_date_status (booking_date, status)`（管理端按日期+状态筛，FR-15/FR-19）。

### 2.4 `operation_log`　管理员敏感操作日志表

支撑需求：NF-14（可审计性，必做项）、NF-03（普通用户不可查看——由接口层 `/api/admin/**` 保证）

| 字段 | 类型 | 可空 | 默认值 | 约束 | 说明 |
|------|------|------|--------|------|------|
| `id` | BIGINT UNSIGNED | 否 | 自增 | 主键 | 日志 ID |
| `operator_id` | BIGINT UNSIGNED | 否 | — | 外键 → `user(id)` ON DELETE RESTRICT | 操作人；RESTRICT 保证日志的操作人不被删除 |
| `operator_username` | VARCHAR(50) | 否 | — | — | **操作人账号冗余快照**：用户改名或被停用后，历史日志仍能显示"当时是谁操作的"（NF-14） |
| `operation_type` | VARCHAR(50) | 否 | — | CHECK ∈ 9 个枚举值¹ | 操作类型，覆盖 NF-14 列明的全部敏感操作¹ |
| `target_type` | VARCHAR(30) | 否 | — | CHECK ∈ ('USER','ROOM','BOOKING') | 操作对象类型 |
| `target_id` | BIGINT UNSIGNED | 是 | NULL | — | 操作对象 ID；对象已删除时置空（如 ROOM_DELETE 成功后） |
| `before_data` | JSON | 是 | NULL | — | 变更前数据快照；新增类操作为 NULL |
| `after_data` | JSON | 是 | NULL | — | 变更后数据快照；删除类操作为 NULL |
| `operated_at` | DATETIME | 否 | 当前时间 | — | 操作时间，写入后不随更新变化 |
| `remark` | VARCHAR(255) | 是 | NULL | — | 补充说明（如取消原因摘要） |

¹ `operation_type` 枚举：`USER_CREATE` 建号／`USER_DISABLE` 停用／`USER_ENABLE` 启用／`ROLE_CHANGE` 角色变更／`ROOM_CREATE` 新增会议室／`ROOM_UPDATE` 修改会议室／`ROOM_DELETE` 删除会议室／`ROOM_STATUS` 启停会议室／`BOOKING_FORCE_CANCEL` 强制取消预约。

索引：主键 `id`；`operator_id`、`operated_at`、`operation_type`、`(target_type, target_id)`。
**表上不设删除标志、脚本不提供删除语句——日志"不能被业务界面删除"（NF-14）**；接口层只提供 GET（说明书 §4.2 #13）。

## 三、索引设计说明

| 索引 | 表 | 列 | 支撑的查询 | 支撑需求 |
|------|----|----|-----------|----------|
| `uk_user_username` | user | username | 登录按账号查唯一行（FR-01）、建号查重（FR-14） | FR-01、FR-14 |
| `uk_room_building_no` | meeting_room | (building, room_no) | 新增会议室查重（FR-03"拒绝重复新增"） | FR-03 |
| `uk_reservation_booking_no` | reservation | booking_no | 预约编号唯一、按编号查单条 | FR-07 |
| `idx_reservation_room_time` | reservation | (room_id, booking_date, start_time, end_time) | **冲突检测**：`WHERE room_id=? AND booking_date=? AND start_time < :endNew AND end_time > :startNew AND status IN (0,1)`。等值列（room_id、booking_date）走索引前缀，范围列（start_time、end_time）在其上做范围扫描——**这条索引就是半开区间冲突判定（FR-09）与占用日历（FR-17）的物理支撑** | FR-09、FR-17、NF-07 |
| `idx_reservation_user_date` | reservation | (user_id, booking_date) | "我的预约"按日期倒序查本人记录（FR-11） | FR-11 |
| `idx_reservation_date_status` | reservation | (booking_date, status) | 管理端按日期 + 状态筛选全部预约（FR-15、FR-19） | FR-15、FR-19 |
| `idx_log_time` / `idx_log_type` / `idx_log_target` | operation_log | operated_at / operation_type / (target_type, target_id) | 管理端按时间/类型/对象查日志（NF-14） | NF-14 |

**冲突检测 SQL（第 9 周实现口径，与说明书 §3.2 同一规则）**：

```sql
SELECT COUNT(*) FROM reservation
 WHERE room_id      = :roomId
   AND booking_date = :date
   AND status IN (0, 1)                -- 只有"待开始 / 进行中"占位；已取消(3)已释放时段
   AND start_time < :endNew            -- ★ 半开区间条件一
   AND end_time   > :startNew          -- ★ 半开区间条件二
 LIMIT 1;
```

并发兜底（NF-07）：该 SELECT 与后续 INSERT 在**同一事务**内，并对目标会议室当日记录加 `SELECT ... FOR UPDATE` 行锁；只靠应用层先查后插存在超订窗口。

## 五、关键设计口径（验收时的"三问"答案 + 三个说明）

### 5.1 三问（任务书第二节的验收问题，课上直接用）

| 问 | 答 |
|----|----|
| **每条预约的开始/结束时间怎么存？** | `start_time`、`end_time`，类型 `DATETIME NOT NULL`。占用区间为**半开区间 `[start_time, end_time)`**：含开始时刻、不含结束时刻，冲突判定 `start_new < end_old AND end_new > start_old`，**首尾相接不算冲突**（FR-09）。另冗余 `booking_date DATE NOT NULL` 便于按日查询与聚合（FR-17、FR-20），并由 CHECK 保证它恒等于 `DATE(start_time)`。 |
| **状态有哪几种取值？** | `reservation.status`：**0 待开始 / 1 进行中 / 2 已结束 / 3 已取消**（NF-08，TINYINT + CHECK）。另有两组独立枚举：`user.status`（ACTIVE/DISABLED）、`meeting_room.status`（ENABLED/DISABLED）。 |
| **删掉一间会议室会不会影响已有预约？** | **会，且被数据库直接拒绝**：`reservation.room_id` 外键 `ON DELETE RESTRICT`——只要该会议室还有预约（不论状态），`DELETE` 即报外键错误 1451，业务层翻译为 `409 该会议室存在有效预约，请先处理预约`（FR-03）。要删必须先处理预约。`user` 同理（不因删用户毁掉预约记录）。 |

### 5.2 说明 1：时间字段为什么用 DATETIME 而不是 TIMESTAMP

`DATETIME` 不带时区转换，存的是"墙上时间"；`TIMESTAMP` 会随服务器 `time_zone` 转换。本系统全部在本机单时区运行、不做跨时区协作，用 DATETIME 不受服务器时区配置影响，且范围覆盖 1000-9999 年（TIMESTAMP 只到 2038）。演示与测试数据固定为 2026-11-02，无歧义。

### 5.3 说明 2：booking_date 是冗余字段，为什么还要存

`start_time` 已含日期信息，`booking_date` 理论上可推导。单独存一列 `DATE` 的理由：① 占用日历（FR-17）与管理端按日筛选（FR-19）都是"按天"查询，等值命中 `(room_id, booking_date)` 联合索引前缀，比对 DATETIME 做范围+函数转换高效且可走索引；② 按日聚合（FR-20）直接 GROUP BY；③ 用 `ck_reservation_date_match` CHECK 强制它与 `DATE(start_time)` 一致，**不允许漂移**，所以不产生脏数据。

### 5.4 说明 3：状态取值与任务书示例不一致的依据

任务书第三节示例给的是 3 态（0 已预约/1 已取消/2 已结束），但任务书同时明确"**图和表只是格式参照，照抄不算完成**"。本组需求清单 V1.1 的 **NF-08** 明确四态：待开始/进行中/已结束/已取消。故按 NF-08 落 4 态（`《周推进计划_第7-8周》§2.2.2` 同口径），并在表注释中逐个列清。

### 5.5 说明 4：状态流转不引入定时器

"待开始→进行中→已结束"的翻转**不写定时任务**（需求清单无此功能，加了属超范围）。第 9 周实现口径：**读取时按当前时间推导展示状态 + 写入时落库校正**。数据库只存 `status` 原值。

### 5.6 说明 5：口令与敏感数据

- `user.password` 只存 BCrypt 摘要（60 字符），**脚本与文档中不出现明文口令**；演示账号与口令只写在根 `README.md`（NF-05）。
- 演示数据不用真实手机号、真实姓名（NF-06），`phone` 均为 138 开头的模拟号段。
- `schema.sql` 收尾自检 SELECT **不打印口令与摘要**，可安全投屏。

## 七、与《系统设计说明书》的口径衔接（★ 需组长裁决的 3 处差异）

《周推进计划_第7-8周》§2.2.1／§4.2.1 与《系统设计说明书》§2.1／§3.2 在**数据库命名与状态编码**上存在 3 处不一致。本文件与 `schema.sql` **按《周推进计划》执行**（本文件的分工依据即该计划），差异逐条登记如下，**请组长在 10-22 检查点 ② 前二选一**，选定后三处（说明书 / 本文件 / 脚本）同步统一：

| # | 项 | 《周推进计划》口径（本文件与脚本采用） | 《系统设计说明书》口径 | 差异影响 |
|---|----|----------------------------------------|------------------------|----------|
| 1 | 预约编号字段名 | `booking_no`，规则 `BK + yyyyMMdd + 4位序号`（§2.2.1、§4.2.1 #11） | `reservation_no`，示例 `MR20261012001`（§3.2 第 7 步、§4.2 #5 出参） | 仅字段名与编号前缀；接口出参字段名（`reservationNo`）不受库列名影响，可保持对外不变 |
| 2 | 预约日期字段名 | `booking_date`（§2.2.1） | `reserve_date`（§3.2 冲突 SQL） | 仅列名；对外入参统一 `date`，不受影响 |
| 3 | 状态编码 | `TINYINT` 0/1/2/3 + CHECK（§2.2.2、§4.2.1 #4，依据 NF-08） | 字符串 `PENDING/ONGOING/FINISHED/CANCELLED`（§3.2 说明 2） | 编码方式；**四态语义两边一致**。若组长选字符串方案，需把 §四 表的 #9 约束改为 VARCHAR 枚举，`schema.sql` 同步 |

**为何建议保留计划口径（TINYINT + booking_no）**：① 任务书示例物理表结构本身就用 `TINYINT ... DEFAULT 0`；② TINYINT 比 VARCHAR 省 3~12 字节/行且比较更快，状态列是冲突检测高频过滤列；③ CHECK 枚举在数字上更不易因大小写/空格脏数据失效；④ 《推进计划》§4.2.1 是本周分工的直接依据。
**对外字段名不受影响**：接口 JSON 里统一 `bookingNo`（或按说明书 `reservationNo`，二选一后统一）——数据库列名与 API 字段名本就解耦（实体层映射）。

> 本节登记即视为《系统设计说明书》§4.4"接口边界变更记录"的**数据库侧补充记录**；路径、方法、入参结构**均未变更**，不属于接口边界改动。
