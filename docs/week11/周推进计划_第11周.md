### 6.1 关键动作的执行顺序（不能乱）

```
10 并发复验（廉价）
      ↓ 通过
灌 1000 条（独立测试库）
      ↓
性能基线：2 接口 × 20 次 → P95 + explain
      ↓
并发 50 同一秒正式执行
      ↓
四类攻击取证
      ↓
缺陷修复 → 逐条回归 → Bug 日志登记/关闭
      ↓
测试数据恢复 → 干净机 README 三步复现
      ↓
报告统稿 + xlsx + 标签
```

> **为什么先 10 后 50**：50 并发脚本一旦有问题，排查成本高；**10 并发是它的廉价替身**（同一脚本、同一判据，只是规模小）。**先花 5 分钟验证脚本本身是同时发，再上 50。**
> **为什么灌数在性能之前、并发之后**：灌 1000 条会**改变数据规模**，并发测试要基于明确的库状态才好复现与核对。**两个测试的数据基线不同，必须在报告里写清各自的基线**（并发前库内条数 ＝ X，性能前库内条数 ＝ Y），否则复现不了。

3. **演示顺序**：讲（问题是什么／比较过哪几个方案／为什么这么设计／每个人做了什么，**按第 7—8 周的设计文档讲，别临场编**）→ 系统（普通用户八步 ＋ 管理员四步）→ 数据（**当场在数据库里查出刚提交的那一行，不是看页面**）→ 测试（**讲一条失败过的用例，和它对应的缺陷是怎么定位、怎么修的**）。
4. **抽查高概率项，本周材料必须撑得住**：
   - 停掉数据库再点会议室列表（**不能出数据**）；
   - 随机指一间会议室一个时段，当场走完普通用户八步；
   - **从九组冲突里随机抽两组，重点抽「首尾相接」**；
   - 从非功能记录里随机指一项，**当场重做一遍**（攻击重发请求、并发重跑脚本），看结果与记录里贴的是不是同一条；
   - **挑 README 里的一句命令，让没搭过这套环境的同学照着执行**；
   - 当场跑一次性能（两个接口各 20 次，看 P95 与报告差多少）；
   - 当场跑一次并发（50 并发同房同时段，看是不是只留下 1 条）；
   - 从报告里指一条标「已关闭」的缺陷，照复现步骤再走一遍，**看还能不能复现**；
   - 用普通用户 token 调一个管理员接口；
   - 抽同学答：**冲突为什么放在后端判？半开区间为什么首尾相接不算冲突？时间字段为什么用 datetime、状态有哪几种取值？**
   - 抽同学讲自己的独立产出（**"协助""参与讨论"不算分工**）；
   - **翻 Git：三周每周每人至少一次提交，`week09-final`、`week10-final`、`week11-final` 三个标签都在**。
5. **判定规则要认**：**任何一项当场做不出来，该项对应的材料按未完成计**——材料写得再全，现场演示不出来也不算。
6. **预答辩结束当天记下问题和整改清单**，提交到 git 仓库，正式答辩（约第 17 周，学院统一组织）之前完成整改；总结报告、最终 PPT 和整改后的系统在正式答辩前定稿。
