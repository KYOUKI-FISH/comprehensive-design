## 1. 并发超卖：50 个请求同一秒抢同一时段

### 1.1 脚本怎么保证"同一秒"（审查时先看这一条）

```python
barrier = threading.Barrier(N)          # 50 个线程
def worker(i):
    ...
    barrier.wait()                      # ★ 50 个线程在这里互相等齐
    marks[i] = time.time()              # 号令枪响后各自记起跑时刻
    st, payload = call("POST", "/bookings", body, tokens[i % 2])
```

- **不是** for 循环顺序发：50 个线程用 `Barrier` 对齐后同一瞬间冲闸门；
- 脚本会算出 **50 个起跑时间戳的跨度（毫秒）**，跨度 < 1000ms 才算"同一秒"，
  不满足时脚本自身判不通过；
- 50 条请求体除 `topic` 外完全一致（同 room、同日期、同起止时刻），差别只在携带的令牌。

### 1.2 判据与实测

| 1 | 并发数 | 10 | **50** |
| 2 | 起跑跨度 < 1000ms（同一秒） | 3.1 ms | **15.6 ms** |
| 3 | 成功条数 | 1 | **1** |
| 4 | 明确失败条数（409 ＋ 占用时段） | 9 | **49** |

| 7 | 库内该时段有效预约条数 | 1 | **1** |

## 2. SQL 注入：4 组载荷 × 4 个注入点 = 16 次

### 2.1 静态证据：全仓库无 `${}` 拼接

```bash
grep -rn '\${' backend/src/main/resources/mapper/     # 无输出
```

4 个 Mapper XML 全部使用 `#{}` 参数绑定。典型写法：

```xml
<!-- 登录：WHERE username = #{username} -->
<!-- 会议室筛选：AND (location LIKE CONCAT('%', #{location}, '%') OR name LIKE ...) -->
```

`LIKE` 的 `%` 由 SQL 侧 `CONCAT` 拼接，**用户输入只作为绑定参数**，不进入 SQL 文本。

### 2.2 载荷与预期

| 编号 | 载荷 |
|------|------|
| P1 | `' OR '1'='1` |
| P2 | `admin' -- ` |
| P3 | `' OR 1=1 #` |
| P4 | `1; DROP TABLE reservation-- ` |

### 2.3 结果（16/16 载荷被当普通字符串处理）

| 注入点 | 请求 | 实测响应 | 结论 |
|--------|------|----------|------|
| G1 登录账号名 | `POST /api/auth/login`，username 塞 4 组载荷 | 全部 `code=401`／`400`，**未返回任何令牌**，无 5xx | 未被注入 |
| G2 会议室位置筛选 | `GET /api/rooms?status=ENABLED&location=<载荷>`（带 user token） | 全部 `code=200`，**返回 0 条**（无任何会议室名称/位置含该串） | 未被注入 |
| G3 预约主题 | `POST /api/bookings`，`topic` 塞 4 组载荷 | 全部 `code=200` 建单成功；`select topic` 回读**与载荷逐字符一致**（`1; DROP TABLE reservation-- ` 被原样存成文本） | 未被注入 |
| G4 管理端状态筛选 | `GET /api/admin/bookings?status=<载荷>` | 全部 `code=400`，`预约状态只能是 PENDING／ONGOING／FINISHED／CANCELLED`（枚举白名单先拦下） | 未被注入 |

**"打不动"就是结论**（计划 §5 卡点 9）：载荷被当普通字符串处理、服务不报错、库内数据完好 —— 这是好结论，
不是"没做"。真正需要警惕的是反过来：如果 P4 生效，`reservation` 表会消失。

### 2.4 库内数据完好性（执行前后对比）

| 项 | 执行前 | 执行后 |
|----|--------|--------|
| `reservation` 表是否存在 | 1（在） | 1（在） |
| `reservation` 行数 | 35 | 35（G3 的 4 条载荷主题先清后写，净增 0） |
| `user` 行数 | 3 | 3 |
| `meeting_room` 行数 | 3 | 3 |

> 表结构、约束、索引均未变化；`DROP TABLE` 载荷未被执行。

### 2.5 一处方法修正（如实记录）

G2 第一轮执行时**没带令牌**，`/api/rooms` 在第 10 周 PR#4 之后已要求登录，返回的是
`code=401 未登录或登录已过期` —— 那是**鉴权拦住了请求，请求根本没走到 SQL**，
拿它当"注入无效"的证据是错的。补上 `Authorization: Bearer <user token>` 后重跑，
才真正打到 `MeetingRoomMapper.selectByCondition`。本记录引用的是**带令牌后的结果**。

## 3. 性能：1000 条数据下的 EXPLAIN 与耗时

### 3.1 数据隔离

灌数在**独立库** `meeting_room_w11perf` 做（`CREATE TABLE ... LIKE` 复制结构，不复制外键），
不动业务库 `meeting_room`，因此第 10 周演示数据完好（NF-15）。
灌数脚本：`tests/week11/04_perf_explain.sql`（递归 CTE 一次插入 1000 条，`count(*) = 1000` 已核对）。

### 3.2 EXPLAIN（1000 条）

| # | 语句 | type | key | rows | 判读 |
|---|------|------|-----|------|------|
| ① | `selectMine`（我的预约，join 会议室） | `index` / `ref` | `uk_room_name` / `idx_reservation_room_time` | 3 / 1 | 驱动表是 `meeting_room`（3 行），每条走 `room_id` 索引，代价随**房间数**增长，不随预约总量线性增长 |
| ② | `selectOccupiedSlots`（占用时段） | `range` | `idx_reservation_date_status` | 5 | 命中索引，未退化为 `ALL` |
| ③ | `correctOverduePending`（**改前**） | **`index`（≈全表）** | `PRIMARY` | **1000** | ★ 瓶颈：`status`、`end_time` 都不是任何索引的前导列 |
| ④ | `correctOverduePending`（**改后**） | **`range`** | `idx_reservation_date_status` | **15** | 补 `reserve_date <= CURDATE()` 后吃到范围扫描 |
| ⑤ | 等价性核对 | — | — | — | 两种写法命中行数 **3 = 3**，无漏校正 |

原始输出：`tests/week11/out/perf_explain.txt`。

### 3.3 耗时对比（隔离库 1000 条，各 300 次取平均）

| 写法 | 平均单次耗时 | 相对 |
|------|-------------|------|
| 改前：`status='PENDING' AND end_time < NOW()` | **3632.6 µs** | 1× |
| 改后：再加 `AND reserve_date <= CURDATE()` | **252.7 µs** | **约 14 倍更快** |

原始输出：`tests/week11/out/perf_bench.txt`。

> 为什么这条值得修：它挂在 `GET /api/bookings/mine` 上，**每打开一次"我的预约"就执行一次**。
> 26 条数据时看不出来，1000 条时单次 3.6ms，量再涨就是线性恶化 —— 属于"现在不疼、答辩现场抽到会疼"的点。

### 3.4 修复与等价性论证（`backend/src/main/resources/mapper/ReservationMapper.xml`）

```sql
UPDATE reservation
   SET status = 'FINISHED', updated_at = CURRENT_TIMESTAMP
 WHERE status = 'PENDING'
   AND end_time < NOW()
   AND reserve_date <= CURDATE()   -- ★ 第 11 周新增，用于命中 idx_reservation_date_status
```

**逻辑等价**：`end_time < NOW()` ⇒ 该预约已经开始过 ⇒ 其 `reserve_date` 必 ≤ 今天；
而 `reserve_date` 与 `start_time` 同日的合法性由库内 CHECK 约束
`ck_reservation_date_match (reserve_date = cast(start_time as date))` 与
`ck_reservation_same_day` 保证，因此新条件**不会漏校正任何一行**。
第 ⑤ 段 EXPLAIN 脚本已用"两种写法命中行数相同"做了实测核对。

**未改表结构、未加索引**（第 11 周冻结，加索引也算改表结构），只改查询写法。

### 3.5 修复后回归（真实库）

| 造的数据 | 调用 `/bookings/mine` 前 | 调用后 | 期望 |
|----------|--------------------------|--------|------|
| 昨天 09:00—10:00，`status=PENDING`（`MRREGRESS01`） | PENDING | **FINISHED** | ✅ 校正仍生效 |
| 今天 23:00—23:30，`status=PENDING`（`MRREGRESS02`） | PENDING | **PENDING** | ✅ 未误伤未开始的预约 |

## 4. 本轮缺陷（Bug 日志候选，按任务书六项齐全）

### 4.1 承接第 10 周条目：W10-01 冲突提示会把"当天全部占用"都显示成本次冲突

| 字段 | 内容 |
|------|------|
| 现象 | 提交一条与 20:00—21:00 冲突的预约（20:30—21:30），409 载荷 `occupiedSlots` 里返回了**当天全部**占用：09:00—11:00、14:00—15:00、20:00—21:00，其中前两条与本次提交**并不重叠** |
| 复现步骤 | ① room2 同一天建 09:00—11:00、14:00—15:00、20:00—21:00 三条；② 再提交 20:30—21:30；③ 看 409 响应 `data.occupiedSlots` |
| 定位到哪 | `BookingService.ensureNoConflict` → `reservationMapper.selectOccupiedSlotsOfRoom(roomId, date, excludeId)`：冲突判定与 409 载荷**共用同一份"当天全部占用"查询结果**（FR-10 的既定设计，前端靠它渲染当天占用条） |
| 怎么修 | **本周未改**。收窄载荷会让前端拿不到当天占用条；给载荷加"是否本次冲突"标记又属于改出参 —— 第 11 周功能/契约冻结，两者都不许做 |
| 回归结果 | 不适用（未改代码）。已确认判定本身正确：只有真正重叠的 20:00—21:00 触发 409，边界 11:00—12:00 不会误判 |
| 当前状态 | **未关闭**。原因：属前端渲染语义 —— 前端应用 `重叠 = start_new < end_old && end_new > start_old` 过滤后再高亮；交接给前端（孙若普），需随前端页面一起改，**不需要后端改接口** |

> 与李牧远在 `docs/week10/03_V1.0现场走通验收记录.md` 中登记的 W10-01 是**同一条**，此处不重复计数，

### 4.2 本周新增：W11-02 超长入参导致 500「服务器内部错误」

| 字段 | 内容 |
|------|------|
| 现象 | 预约主题 >100 字、联系人 >50 字、会议说明 >255 字、取消原因 >200 字时，接口返回 `code=500 服务器内部错误`，库里也没有落库 —— 用户只是**输多了一个字**，却看到"系统故障" |
| 复现步骤 | ① user1 登录；② `POST /api/bookings`，`topic` 填 101 个 `T`；③ 观察响应 `code=500`；④ 把 `topic` 换成 50 字则成功 —— 说明确实与长度相关 |
| 定位到哪 | `BookingService.validateRequired()` 只校验了"非空／人数>0"，**没有长度上限**；字符串直接进库，超出列宽（`topic` 100／`contact` 50／`purpose` 255／`cancel_reason` 200）触发 `DataIntegrityViolation`，被 `GlobalExceptionHandler` 的兜底分支转成 500。管理端 `AdminRoomService`／`AdminUserService` 早有长度校验，**预约侧漏了**（同一类问题只在一条链路上修过） |
| 怎么修 | `BookingService` 增 `TOPIC_MAX_LENGTH=100 / CONTACT_MAX_LENGTH=50 / PURPOSE_MAX_LENGTH=255 / CANCEL_REASON_MAX_LENGTH=200`，在 `validateRequired()` 与 `cancel()` 里拦成 `400` 并给中文提示；`AdminBookingService.forceCancel` 补 `MAX_REASON_LENGTH=200`（原来只有 ≥5 的下限） |
| 回归结果 | 101 字主题 → `400 会议主题不能超过 100 个字符`；51 字联系人 → `400`；256 字说明 → `400`；201 字取消原因（用户侧／管理端）→ `400`；**边界值 100 字主题仍成功**（不误伤）；TC-01～TC-06 复跑 6/6 通过 |
| 当前状态 | **已关闭** |

### 4.3 观察项（不计缺陷，交组长定口径）

- **参会人数未与会议室容量比对**：room1 容量 20，提交 `attendeeCount=100` 仍成功。
  查需求清单与任务书，**没有"人数不得超过容量"的条目**，故不按缺陷登记；

**两个环境坑（会让人误判"后端挂了"）**：

1. 沙箱环境设了 `HTTP(S)_PROXY` 指向 127.0.0.1，脚本已内置绕过；用 `curl` 手工验时要加 `--noproxy '*'`；
2. 本机 MySQL root 是**空口令**，起后端要 `DB_PASSWORD=''` 且 `env -u SERVER__PORT -u SERVER_PORT`。
