# 技术选型报告（第6周）

> **命名说明**：本报告架构候选按 `A1／A2`、数据库候选按 `B1／B2` 编号，**刻意回避"方案 A／方案 B"字样**——需求侧铁律中"方案 A"专指**自由时间段预约**方案（见第 4 周《角色说明》《范围说明》），沿用同名会在"同源核对"时把两件事混为一谈。候选编号与《周推进计划》§4.1 一致。
> **依据来源规则**：每一行依据均追到具体出处（本组前周走查事实／官方文档／同类系统做法）；"大家都这么用""普遍采用"一类说法不作为依据。

## 一、架构选型比较

| 候选方案 | 好处 | 代价 | 本组是否选它 | 依据 |
|--------|------|------|--------------|------|
| **A1：单体应用（后端模板渲染，页面由后端直出）** | 1. 只需启动一个进程，启动步骤最少；<br>2. 无跨域问题，联调环节少；<br>3. 部署与运维最简单 | 1. 页面交互能力弱，日历／时间选择／列表筛选需服务端拼 HTML，开发效率低；<br>2. 前端无法独立构建与迭代；<br>3. **与已定的前端技术栈冲突** | **不选** | 1. 本组前端技术栈已定为 **Vue3 + TypeScript + Element Plus + Vite**（见《技术栈清单》），该栈是需独立构建的 SPA，模板渲染单体无法承载；<br>2. 第 5 周需求清单 FR-05／FR-06（查询会议室）、FR-07（提交预约）需要日期时间选择、列表筛选等交互控件，服务端拼页难做；<br>3. 官方文档：Vue 组合式 API / 单文件组件面向单页应用，配 Vite 构建（Vue 官方文档、Vite 官方文档）；<br>4. 结论：选 A1 等于推翻《技术栈清单》，自相矛盾 |
| **A2：前后端分离（Vue3 SPA + 后端 REST API）** | 1. 前端用 Element Plus 现成组件，日历／表格／表单开发快；<br>2. 前后端接口清晰，各有人手可并行开发；<br>3. 后端只出 REST 接口，前端可独立迭代 | 1. 需同时启动前端（Vite dev server／构建产物）与后端两个进程，启动步骤多一步；<br>2. 需配置跨域（CORS）与接口文档；<br>3. 联调成本高于单体 | **选它** | 1. 与《技术栈清单》一致：前端 Vue3 + TS + Element Plus + Vite，后端 Spring Boot 3.2 + MyBatis 出 REST，本就是分离形态；<br>2. 《周推进计划》§3 分工为前端（刘宇轩）／后端（虞业宸）分头负责，分离架构才能并行、互不阻塞；<br>3. 联调成本可用统一返回体 + OpenAPI／Knife4j 接口文档压到可接受范围；<br>4. Element Plus 官方文档：提供表单、日历、表格、弹窗等中后台组件 |

**架构选型结论**
采用 **A2（前后端分离：Vue3 SPA + Spring Boot REST）**。
**预测问题**：前后端分离后最容易踩的坑是**跨域与接口字段不一致**——需在第 7 周接口设计阶段把接口路径、字段名、错误码、分页格式一次性约定死，并以 OpenAPI 文档固化。另 SPA 需先构建（或起 Vite 开发服务器），README 里必须把"启动后端 + 启动前端"两步都写清，否则验收同学只起了半边，页面打不开。

## 二、数据库选型比较

| 候选方案 | 好处 | 代价 | 本组是否选它 | 依据 |
|--------|------|------|--------------|------|
| **B1：MySQL 8.0（关系型数据库）** | 1. 支持事务与行级锁，适合预约的并发控制；<br>2. 结构化数据，用户—预约—会议室多表关联清晰；<br>3. 与 Spring Boot + MyBatis 集成成熟 | 1. 需先设计表结构，且**需在本机安装 MySQL 服务**，比文件型数据库多一步安装；<br>2. 对"灵活字段"支持不如文档数据库 | **选它** | 1. 第 5 周需求清单 FR-09 要求"检测同一会议室同一时段是否已被预约"，防超订必须靠事务保证一致性；<br>2. 需求存在"用户—预约—会议室"多表关联（见第 5 周 DFD 的 D1～D3）；<br>3. MySQL 官方文档：InnoDB 存储引擎支持事务（ACID）与行级锁；<br>4. 第 2 周竞品走查记录：学校原有会议室／教室预约类系统采用关系型数据库 |
| **B2：MongoDB（文档型数据库）** | 1. 模式灵活，字段可随时增减；<br>2. JSON 文档便于前端直接使用；<br>3. 天然支持水平扩展 | 1. 多文档事务支持较弱，预约场景易超订；<br>2. 关联查询需多次操作，代码量大；<br>3. 本学期无 NoSQL 专项学习，学习成本高 | **不选** | 1. 本项目核心诉求是数据一致性（FR-09 防重复预订），而 MongoDB 的优势在"非结构化／半结构化数据"（MongoDB 官方文档），与本项目结构化诉求不匹配；<br>2. 需求清单中无"动态字段""日志型数据"等 MongoDB 优势场景；<br>3. 本学期未安排 NoSQL 学习，成本不划算 |

**数据库选型结论**
采用 **B1（MySQL 8.0）**。
**预测问题**：MySQL 需本机安装，是"换机器照 README 跑起来"中**安装负担最重的一环**——README 必须把安装与初始化写成一步一条命令，建表与种子数据脚本随仓库走，否则验收同学会卡在装库上。运行时预约高峰需关注连接池大小，避免连接耗尽。

## 三、选型结论与风险说明（必须包含"会遇到什么问题"）

1. **架构层面**：前后端分离后，跨域配置与接口字段一致性是首要风险；第 7 周接口设计阶段须把接口路径、字段名、错误码、分页格式一次性约定死，并以 OpenAPI 文档固化。前后端各一人并行开发，多人改同一模块时用 feature 分支减少冲突。
2. **数据库层面**：MySQL 8.0 需本机安装，README 必须提供一步一条命令的安装与初始化步骤；预约高峰期需配置连接池，否则可能连接耗尽。
3. **部署层面**：本组选择**本机直接运行**（非容器化），验收环境为同学的本机——只需 JDK 17 与 Node.js，不引入 Docker Desktop／WSL2 等重安装项（详见《技术栈清单》部署方式一节）。理由：第 6 周验收唯一标准是"换一个人、换一台机器照 README 把系统跑起来、不增加安装负担"。
4. **整体风险**：当前选型以"跑得起来、验收通过"为优先。若后续需求变更（如加入消息推送、移动端），需重新评估架构；本学期明确不实现人脸识别、物联网设备控制、3D 场景、智能推荐、重复预约、多级审批、消息推送、统一身份认证对接、移动端原生应用共 9 项，故不引入相关技术。
