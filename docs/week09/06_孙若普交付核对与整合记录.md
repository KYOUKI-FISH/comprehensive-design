## 3. 本次实际补的两处缺口

### 3.1 FR-08 时间规则（`frontend/src/views/BookingView.vue`）

仓库原页面只有必填校验，**没有任何时间合法性判断**——用户填 14:00 → 09:00 或 08:00 → 20:00 都能提交，全靠后端兜底。任务书 §4.4 要求预约表单页具备「时间规则」，§2 目标将其列为本周目标。

补法：

- 新增 `MAX_DURATION_MINUTES = 8 * 60` 与 `toMinutes()`（HH:mm → 当日分钟数，格式非法返回 null）；
- 新增 `validateTimeRule()`，返回 `string | null`，覆盖三条：结束晚于开始／不跨天／不超过 8 小时；
- 挂到 `endTime` 的 `FormRules` validator 上，用户在界面上改结束时间即时提示；
- `onSubmit()` 开头再显式调一次 `validateTimeRule()` 兜底——因为用户可能只改了开始时间，`endTime` 的 change 不会触发。

**为什么把「结束 ≤ 开始」与「跨天」合并成一句**：本页日期是独立字段 `form.date`，起止时间只填 HH:mm，跨天在结构上无法通过选日期发生，只会表现为结束时刻早于开始时刻，分钟差 `<= 0` 与跨天是同一件事。

### 3.2 FR-02 路由角色守卫（`router/index.ts` + 新增 `views/ForbiddenView.vue` + 新增 `src/router/meta.d.ts`）

仓库原守卫**只判断是否登录，不判断角色**。后果：管理员登录后可以直接在地址栏输入 `/bookings/new` 进预约页提交预约，与角色说明权限矩阵「管理员提交预约：不允许」相悖。

补法：

- `/bookings/new` 加 `meta: { role: 'USER' }`；
- 守卫在登录校验之后追加：`if (requiredRole && session.user?.role !== requiredRole) return { name: 'forbidden' }`；
- 新增 `ForbiddenView.vue`（Element Plus `el-result` 风格，匹配仓库现有 UI），按 `?from=` 参数给出具体原因，而不是只甩一句「无权访问」；
- 新增 `src/router/meta.d.ts`，用 `declare module 'vue-router'` 扩展 `RouteMeta`，声明 `public`／`title`／`role` 三个字段——否则 `to.meta.role` 在严格模式下过不了 `vue-tsc`。

**这一处与后端对齐**：`AuthInterceptor` 已对 `/api/admin/**` 做 ADMIN 校验；本次补的是前端侧的角色门，让后端 403 不必成为用户唯一的反馈。

## 4. 为什么不整体替换

技术上可行（他的版本自测 38/38 + 46/46 全绿），但**代价大于收益**：

1. **丢失 Element Plus 基线**：第 6 周定稿的技术栈是 Element Plus，4 个页面全部基于它。整体替换等于把第 6 周的骨架推倒重来。
2. **丢失请求层统一口径**：仓库 `http.ts` 用 axios 拦截器带令牌、拆 `ApiResponse` 外壳、把异常翻译成中文；他的 fetch 版需重写且要重新验证 401 处理、超时处理与 `auth:expired` 事件。
3. **需重新跟后端联调**：仓库后端已跑通（虞业宸 30 条用例全绿 + 本机真实联调 9 分支），他的版本是对着自家 mock 调的，字段与真实后端未对齐（他自己在 README §8 第 2 条也提示了这一点）。
4. **他自带的 `mock-server/` 不能入库**：任务书 §2.1 自查第 1 条要求「停掉数据库再点会议室列表，不得照样出数据」，mock 若被误当正式后端会直接违反该条。

**收益侧则很小**：逐条核对下来（§2），他的 17 个功能点里 15 个仓库已有或等价，真正缺的只有 2 个，已经补齐。为了这 2 个点推倒重建，不划算。
