## 2.4 ★ 本周打出的两个真 bug（这才是本周最有价值的产出）

> 这两个都是**实测打出来的**，不是代码走查猜的。

### 2.4.1 Bug 1：并发超卖（★ 第 11 周硬指标的直接拦路虎）

| 项 | 内容 |
|---|---|
| **现象** | 10 个并发抢同一间会议室同一时段 → **5 条成功**（最差一次 10 条全成功），库内有效预约 5 条 |
| **第一版做法** | ① `SELECT ... FROM meeting_room WHERE id=? FOR UPDATE` 锁会议室行 ② 普通 `SELECT` 查占用行 ③ 判定 ④ INSERT |
| **根因** | **只锁会议室行不够**。MySQL 默认隔离级别 REPEATABLE READ 下，普通 `SELECT` 是**快照读**——读的是事务开始那一刻的快照，**看不到别的事务刚提交的记录**。锁只保证"请求排队"，排队后每个事务仍读各自的旧快照，于是**全部判"无冲突"** |
| **修法** | 冲突检测的查询改用**锁定读（当前读）**：`SELECT ... FOR UPDATE` 读的是最新已提交数据。Mapper 拆成两个方法——只读版（详情页展示用，不加锁）＋ 锁定读版（**冲突检测专用**） |
| **锁顺序** | 固定为 **先锁 `meeting_room` 行 → 再锁该会议室当日的 `reservation` 行范围**，所有并发请求顺序一致 → **不会死锁** |
| **修后实测** | **10 并发：1 成功 / 9 冲突 / 库内 1 条**<br>**50 并发：1 成功 / 49 冲突 / 库内 1 条**（第 11 周硬指标已提前达标） |
| **附带发现** | 50 并发下"其他（500／超时）"为 **0 条**，证明预约编号方案（自增主键派生）在并发下**不撞唯一键**。若沿用第 8 周注释里的"当日 3 位流水号"，并发下会大量报 500 → **脚本注释已同步改** |

### 2.4.2 Bug 2：`LocalDateTime` 解析失败（★ 表单根本提交不了）

| 项 | 内容 |
|---|---|
| **现象** | 前端提交 `startTime: "2026-10-27 09:00"` → 后端 400，`DateTimeParseException: Text '2026-10-27 09:00' could not be parsed at index 10` |
| **根因** | `application.yml` 里的 `spring.jackson.date-format` **只对 `java.util.Date` 生效，对 `LocalDateTime` 无效**——Spring Boot 自动注册 `JavaTimeModule`，它按 ISO-8601 解析（要 `T` 分隔符） |
| **修法** | 新增 `JacksonConfig`，用自定义反序列化器**同时接受** `yyyy-MM-dd HH:mm` 与 `yyyy-MM-dd HH:mm:ss` 两种精度；输出统一 `yyyy-MM-dd HH:mm:ss` |
| **修后实测** | 表 1 第 4 行「通过」，浏览器提交返回 `MR20261027043` 并**落库** |

> **教训（值得写进第 11 周的测试要求）**：**接口自测通过 ≠ 页面能用**。
> 前端传的参数格式必须由后端**显式支持**，不能靠"约定"——这次的坑是两边都"以为对方会处理"。
