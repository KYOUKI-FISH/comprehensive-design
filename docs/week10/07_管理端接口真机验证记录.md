### 1.1 建库过程中踩的三个坑（写下来省下次时间）

| # | 现象 | 根因 | 解法 |
|---|------|------|------|
| 1 | `--initialize` 报 `unknown variable 'validate_password.policy=LOW'`，随后数据目录被标记为 **unusable** | `my.ini` 里写了 `validate_password.policy`，但该变量属于密码插件，**初始化阶段插件尚未加载** | 从 `my.ini` 删掉这一行；要改策略等实例起来后用 SQL 改。已废弃的 `D:\dev\mysql-data` 必须整个删除才能重新初始化 |
| 2 | `netstat` 看到 3306 在 LISTENING，`mysql` 却报 `10061 拒绝连接` | 用 `nohup ... &` 启动，子进程随命令结束被回收，**只剩 netstat 的残留视图** | 用后台任务方式常驻，不要依赖 shell 的 `&` |
| 3 | 后端起来后监听 **53798** 而不是 8080，报 `Port already in use` | 运行环境里有 `SERVER__PORT` 环境变量，Spring Boot 的松散绑定把它当成了 `server.port` | 启动命令前加 `env -u SERVER__PORT -u SERVER__HOST`。**虞业宸 `06` 文档第 143 行记录过同一个坑**，两侧独立撞上，说明这是本机环境的固有特性 |

另：本机 `http_proxy` 会劫持 `127.0.0.1`，所有 `curl` 必须带 `--noproxy '*'`，否则表现为"服务明明起来了却连不上"。这条虞业宸也记录过（`06` §8 注）。

### 1.2 复现命令

```bash
# 启动数据库（后台常驻）
D:/dev/mysql-8.0.46-winx64/bin/mysqld.exe --defaults-file=D:/dev/mysql-8.0.46-winx64/my.ini --console

# 初始化（首次）
mysql -h 127.0.0.1 -u root -p --default-character-set=utf8mb4 < database/01_schema.sql
mysql -h 127.0.0.1 -u root -p --default-character-set=utf8mb4 < database/02_seed.sql

# 启动后端（注意排除 SERVER__PORT）
cd backend && mvn -DskipTests package
env -u SERVER__PORT -u SERVER__HOST DB_PASSWORD='<本机口令>' java -jar target/meeting-room-backend-1.0.0-SNAPSHOT.jar

# 探活
curl --noproxy '*' http://127.0.0.1:8080/api/health
# → {"code":200,...,"database":"UP"}
```

且前端拿到的是 409 业务提示而不是数据库外键异常 —— NF-10 达标。

#### 关于 11-6 用 400 而不用 409 的判断

我在实现时用的 `CODE_PARAM_ERROR`（400），实测也确认是 400。**这不是缺陷，是刻意选择**：

- 409 的语义是"请求本身没问题，当前资源状态不允许"（如 11-4 删不掉）。
- 重名是**请求参数本身不合法**——换个名字就能通过，属参数错误。
- 且与 #12 建号重名（「账号已存在」400）保持同一口径，两侧一致。

如果第 11 周的统一测试要求重名返回 409，那是一次**口径调整**，两处要一起改，不能只改一处。

### 3.7 越权拦截（NF-03）

| 用例 | 令牌 | 接口 | 业务码 | 判定 |
|------|------|------|--------|------|
| 14-1 | `user1`（USER） | `GET /api/admin/bookings` | 403「无权访问该功能」 | ✅ |
| 14-2 | `user1` | `PUT /api/admin/bookings/2/cancel` | 403 | ✅ |
| 14-3 | `user1` | `GET /api/admin/users` | 403 | ✅ |
| 14-4 | `user1` | `GET /api/admin/logs` | 403 | ✅ |

> **HTTP 状态码说明**：以上响应体的 **HTTP 状态码都是 200**，业务码在 `code` 字段里。
> 这是第 6 周就定下的统一响应约定（`ApiResponse` 信封：业务失败也用 HTTP 200，错误由 `code` 表达），
> **不是缺陷**。前端 `request()` 拆壳时按 `code` 判断。第 11 周若被问"越权怎么返回 200"，
> 答案是"HTTP 200 + 业务码 403，全项目一致"。

### 3.8 CHECK 约束实测

| 用例 | 插入值 | 期望 | 实测 |
|------|--------|------|------|
| 15-1 | `operation_type='HACK_OPERATION'` | 拒绝 | `ERROR 3819`：`Check constraint 'ck_log_operation_type' is violated.` ✅ |
| 15-2 | `target_type='HACK_TARGET'` | 拒绝 | `ERROR 3819`：`Check constraint 'ck_log_target_type' is violated.` ✅ |

15-1／15-2 证明 **MySQL 8.0.16+ 的 CHECK 是真正执行的**（8.0.16 之前只是解析不执行），

写错类型时先被 Java 拦下给出中文提示，绕过 Java 也会被数据库拒绝。
