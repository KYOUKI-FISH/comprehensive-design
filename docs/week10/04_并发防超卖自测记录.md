## 2. 并发防超卖（攻坚点 1，第 11 周 50 并发的硬指标预演）

**方案**：同一事务内 ① `SELECT ... FOR UPDATE` 锁 **meeting_room 行**（不是 reservation 行）→
② 按半开区间查冲突 → ③ 插入。三步同事务，行锁把同间会议室的提交串行化（NF-07）。

**用例**：10 个并发 HTTP 请求同时抢 room1 2026-11-06 09:00-10:00（`curl &` 同时发出）。

## 3. 预约编号方案改造（攻坚点 2）

**弃用**："MR + yyyyMMdd + 当日 3 位流水号"——两间会议室同日并发提交可能取到同一个
"当日最大值"，撞唯一键 `uk_reservation_no`，只能靠重试兜底。

**改为（自增主键派生）**，三步同一事务：

1. 随机 32 位十六进制占位串满足 `NOT NULL UNIQUE`；
2. `INSERT`，`useGeneratedKeys` 回填自增主键；
3. `MR + yyyyMMdd + 左补零主键` 派生正式编号，`UPDATE` 回填。

主键单射 ⇒ 编号唯一，**从根上没有撞键窗口**，"查最大值""重试"两步整体删除。
`schema.sql`／`database/01_schema.sql`／`02_数据库与接口设计.md`／实体注释已同步（只改注释，不改表结构）。

**用例**：两室交替、同一天不同时段，10 个并发请求：

- 10/10 成功、0 失败；编号 `MR20261107017`～`MR20261107026`，**互不相同**，全部 `MR+8位日期+3位补零主键` 格式；
- 全表终态 **26 条数据 = 26 个唯一编号**，无一撞键；
- 跨日期正确：id=8 落在 11-03 → `MR20261103008`；id=9 落在当天 → `MR20261028009`。

## 6. 状态四态（NF-08，读取时推导 + 落库时校正，不引入定时器）

"我的预约"实测（user1）：

| 库存状态 | 时段 | 展示状态 | 说明 |
|---|---|---|---|
| PENDING | 2026-11-02 09:00 | PENDING | 未来 → 待开始 |
| CANCELLED | 2026-11-02 14:00 | CANCELLED | 取消态冻结，不随时间变 |
| PENDING | 2026-10-12 09:00（已过去） | **FINISHED** | 读取时校正落库并展示 |

推导边界（半开区间，与冲突判定同一套区间语义）：`now < start` → PENDING；
`start ≤ now < end` → ONGOING；`now ≥ end` → FINISHED。
