**没有 DELETE 的两个接口是设计如此，不是漏写：**

- `#12 用户管理` 只做**启停**（`status` 置 `DISABLED`），不做物理删除 —— `operation_log.operator_id` 是 `ON DELETE RESTRICT`，删用户会连带删不掉日志链；且 NF-14 要求"日志的操作人可追溯"。
- `#13 操作日志` **不提供 DELETE／PUT** —— NF-14 原文"日志不能被业务界面删除"。`OperationLogMapper` 的类注释里写明了这条约束，接口层也没有对应方法。

### 2.1 越权拦截（NF-03）

`AuthInterceptor` 在 `WebConfig` 里注册为 `addPathPatterns("/api/**")`，`preHandle` 中对
`path.startsWith("/api/admin/")` 且 `role != ADMIN` 直接返回 403「无权访问该功能」。
4 个新 Controller 全部落在 `/api/admin/` 前缀下，**不需要各自写权限判断**，也不会漏。

## 3. 操作日志写入（NF-14）——四类敏感操作全覆盖

### 3.1 类型对照

| NF-14 要求的敏感操作 | `operation_type` | 写入位置 |
|---------------------|------------------|---------|
| 新增用户 | `USER_CREATE` | `AdminUserService.create` 第 114 行 |
| 停用用户 | `USER_DISABLE` | `AdminUserService.update` 第 228–244 行 |
| 启用用户 | `USER_ENABLE` | 同上 |
| 角色变更 | `ROLE_CHANGE` | 同上 |
| 新增会议室 | `ROOM_CREATE` | `AdminRoomService.create` 第 103 行 |
| 修改会议室 | `ROOM_UPDATE` | `AdminRoomService.update` 第 193 行 |
| 启停会议室 | `ROOM_STATUS` | 同上（只改状态时选此类） |
| 删除会议室 | `ROOM_DELETE` | `AdminRoomService.delete` 第 239 行 |
| 强制取消预约 | `BOOKING_FORCE_CANCEL` | `AdminBookingService.forceCancel` |

`schema.sql` 的 `ck_log_operation_type` CHECK 约束限定的正是这 9 个值，`OperationLogService.ALLOWED_TYPES` 与之逐值对齐，**多一个写不进、少一个编译期查不出但 INSERT 会报 3819**，所以在 Java 侧先拦一道给出中文提示。

### 3.2 同事务（这是 NF-14 真正的考点）

"操作成功了但日志没写"是审计链断裂，且事后无法补救 —— 没人记得当时谁取消的。
因此**每个写日志的方法都标了 `@Transactional(rollbackFor = Exception.class)`**，业务变更与日志 INSERT 在同一事务里，任一失败整体回滚。

```java
@Transactional(rollbackFor = Exception.class)
public ReservationDetailDTO forceCancel(Long id, String reason) { ... }
```

### 3.3 一个必须说清的设计取舍：改姓名／电话／密码**不写日志**

`schema.sql` 的 9 个类型里**没有"用户信息修改"**。第 11 周"不改表结构"，本周也守这条，所以加不了新类型。

**选择：不写。** 而不是硬塞一个 `ROLE_CHANGE`。

理由：如果为了"有记录"把改电话写成 `ROLE_CHANGE`，那么将来审计时按类型筛"角色变更"，
会冒出一堆**根本没改过角色**的记录 —— 这比不记更糟，因为审计者会把假记录当成线索去追。

依据：NF-14 列举的敏感操作是"新增／停用用户、新增／删除会议室、强制取消预约、角色变更"，
**修改个人资料不在其中**。不写是口径正确，不是偷懒。

代码位于 `AdminUserService.update` 第 228–244 行，`logType` 为 `null` 时整段跳过。

### 3.4 `before_data` / `after_data` 的 JSON 转义

取消原因来自用户输入，直接拼 JSON 会写出坏 JSON 让 JSON 列插入失败。
`AdminBookingService.escape` 处理了引号与反斜杠，用例 `原因含引号被正确转义` 断言实际输出为
`"主讲人说\"取消\"，场地空出"`。

## 4. 关键业务判定（每条都有对应用例）

### 4.1 强制取消（#10，FR-16）

| 判定 | 失败码 | 提示语 |
|------|--------|--------|
| 原因空／少于 5 字符 | 400 | 请填写取消原因（不少于 5 个字符） |
| 预约不存在 | 404 | 预约不存在 |
| 已是 `CANCELLED` | 409 | 已取消的预约不能重复取消 |
| 非 `PENDING`（`ONGOING`／`FINISHED`） | 400 | 带中文状态名的说明 |
| 更新影响 0 行（并发被抢先） | 409 | 该预约状态已被他人变更，请刷新后重试 |

**"先查后改"的竞态：** 只靠前三条校验会留下窗口 —— 两个管理员同时点，两个都通过校验、都写一次取消原因。
所以 `updateStatusToCancelled` 的 `WHERE` 带 `status = 'PENDING'`，让数据库做原子判定：只有一个能更新到行，另一个返回 0 行触发 409。

```sql
UPDATE reservation SET status = 'CANCELLED', cancel_reason = #{cancelReason}, updated_at = #{now}
WHERE id = #{id} AND status = 'PENDING'
```

### 4.2 删除会议室（#11，FR-03）

```
countByRoomId(id) > 0  →  409「该会议室存在有效预约，请先处理预约（当前挂着 N 条记录）」
```

**数全部状态，不是只数未完成的。** 因为 `reservation.room_id` 的外键是 `ON DELETE RESTRICT`，
拦的是**所有引用行**；只数 `PENDING` 会放行一个注定失败的请求，前端拿到的是数据库外键异常而不是业务提示（违反 NF-10）。

### 4.3 用户管理的三条护栏

| 护栏 | 为什么 |
|------|--------|
| 不能停用当前登录的管理员自己 | 一个人把自己停了，下次登录进不来，也没人会来救 |
| 不能把最后一个可用管理员降级／停用（`countActiveAdmins() <= 1` → 400「系统至少需要保留一个可用状态的管理员账号」） | 系统锁死，只能改库救 |
| 停用后 `tokenStore.revokeAllOf(id)` | 不停用只置状态的话，已签发的令牌还能用到过期 —— 停用等于没停（NF-05） |

密码 ≥ 6 位、BCrypt（cost 10）入库；`UserVO` 不含 `password` 字段，**不是"返回了但置空"，是根本没有这个字段**，序列化不出去。

### 4.4 日志查询的日期边界

```sql
l.operated_at < DATE_ADD(#{endDate}, INTERVAL 1 DAY)
```

**不是 `<= #{endDate}`。** `operated_at` 是 `DATETIME`，`<= '2026-11-04'` 会被当成 `<= '2026-11-04 00:00:00'`，
**当天的日志一条都查不到**。用例 `日志日期边界正确` 断言 SQL 里出现 `INTERVAL 1 DAY` 和 `l.operated_at <`。

### 4.5 `operation_log` 没有 `ip` 列

接口说明里 `ip` 是出参字段，但表里没有这一列，且本周不改表结构。
`AdminLogService` **显式 `row.setIp(null)`**，而不是留着字段不给值 —— 显式置空让下一个人读代码时知道这是已知缺失，不是忘了赋值。

## 5. 不连库也能验的部分：Mapper XML 自检

本机没有 MySQL，最怕的是"一启动就报 MyBatis 异常"这类低级错误在提交后才暴露。
`MapperXmlParsingTest` 用 `XMLMapperBuilder` 直接解析 4 个 XML，**不需要数据源**，能提前发现：

- SQL 语法错、`<if>` 标签没闭合
- `#{}` 占位符与被引用的属性名对不上
- `resultType` 全限定名写错、别名没注册
- `<if test="...">` 引用了 DTO 上不存在的属性
- **接口方法与 XML 语句一一对应**（反射扫 Mapper 接口的所有方法，`hasStatement` 逐个确认）

其中 3 条断言值得单独记一笔：

1. **`动态条件拼接`** 精确断言日期区间只留 **2** 个占位符（而不是"至少 3 个"）—— 因为不设分页时 `LIMIT` 整段不拼，占位符数量恰好等于拼进去的条件数。
2. **`分页条件`** 不能搜 `contains("LIMIT")`：`adminColumns` 里取"最后一条强制取消日志"的标量子查询自带 `LIMIT 1`，直接搜会被它命中，用例永远为真、什么也测不出来。改为**逐字符扫括号深度，只在深度 0 处找 `LIMIT`**。
3. **`接口与XML一一对应`** 这条最救命：改 Mapper 接口忘了写 XML，编译照过，运行才 `BindingException`。
