### 2.1 第 5 步为什么是本周的胜负手

这一步同时验三件事，任何一件缺了都不能算过：

1. **冲突检测**（FR-09）：半开区间 `[start, end)` 判定，`09:30 < 10:00 AND 10:30 > 09:00` → 冲突；
2. **错误提示**（FR-10、NF-10）：不是 500、不是白屏，是**中文业务提示**；
3. **被占用时段的返回与展示**：后端在 409 的 `data.occupiedSlots` 里给出具体时段，页面必须渲染出来。

本次三项都成立，截图里能同时看到提示条与「本次冲突的时段」区块。

### 2.2 状态四态的实测分布（NF-08）

| 状态 | 库中原始值 | 页面显示 | 说明 |
|------|-----------|----------|------|
| `PENDING` 待开始 | PENDING | 待开始 | 第 4 步新建的那条 |
| `ONGOING` 进行中 | — | 进行中（0 条） | 本次验收窗口内没有跨"当前时刻"的预约，**未构造到**（见 §5 未覆盖项） |
| `FINISHED` 已结束 | PENDING（今日已过时段） | **已结束** | 说明状态是**读取时推导**的，不是库里的死值 |
| `CANCELLED` 已取消 | CANCELLED | 已取消 | 用户取消 ＋ 管理员强制取消各 1 条 |

> **★ 关键**：今天（11-02）09:00–11:00 的种子预约在库里仍是 `PENDING`，页面上显示「已结束」——
> 这正好证明前端**没有**按时间自己算状态，而是用后端 `ReservationStatusPolicy.derive` 的结果（NF-08 单一口径）。

### 3.1 为第 3 步造的"异常预约"

管理员第 3 步要求取消一条**异常**预约，而强制取消只对 `PENDING` 生效（`AdminBookingService.forceCancel`
里 `只有待开始的预约可以强制取消`）。验收当天库内所有种子预约都已"结束"或"取消"，没有可取消对象。

因此先用 `user2` 从页面正常提交一条 **2026-11-04 15:00–16:00 @ 逸夫楼A202**
（预约号 `MR20261104061`，主题「临时占用（待管理员处理的异常预约）」），再由 `admin` 强制取消它。

> 这条**不是手工改库造出来的**：走的是正常提交接口 + 正常强制取消接口，符合 QR-03「不依赖手工改数据」的口径。

## 7. 复现步骤（下一次验收照这个走）

```bash
# ① 起库（便携实例，仅本地回环）
mysqld --defaults-file=<my.ini> --console &

# ② 起后端（★ 必须显式给 DB_PASSWORD，否则 database=DOWN 但服务照常"启动成功"）
DB_PASSWORD='<本机口令>' java -jar backend/target/meeting-room-backend-1.0.0-SNAPSHOT.jar

# ③ 探活：只认 database 字段
curl --noproxy '*' http://127.0.0.1:8080/api/health
# → {"code":200,...,"database":"UP"}

# ④ 起前端
cd frontend && npm run dev     # http://localhost:5173

# ⑤ 打开 http://localhost:5173/login，用 README「默认账号」里的 user1 / admin 逐步入 §2、§3 的表格
```

> **两个本地环境坑**（都已在 `07_管理端接口真机验证记录.md` 记录过，这里只复述结论）：
> ① 本机 `http_proxy` 会劫持 `127.0.0.1` 的回环连接，所有 `curl` 必须带 `--noproxy '*'`；
> ② 运行环境里若存在 `SERVER__PORT`，Spring Boot 会把它当成 `server.port`，表现为"端口莫名其妙不是 8080"。
