# 接口响应口径变更说明（BUG-07，第 12 周）

> 适用范围：第 12 周预答辩前的代码与文档口径。
> 历史归档（week03／06／07-08／09／10）、week11 取证目录 `evidence/` 与已打标签版本一律不回改；本文件以「新增说明」的方式纠偏。

## 1. 变更原因

任务书对并发冲突的判据写的是「**409 ＋ 占用时段**」。第 11 周取证时，本组所有业务失败都返回 `HTTP 200`，真正的失败信号藏在响应体 `code` 里（50 并发为 200×50、其中 49 条 `body.code=409`）。功能可用，但传输层看不出失败，用 `curl` 直查状态行或看浏览器 Network 面板时会被问到。

本次只处理这一个问题：**让 HTTP 状态行与 `body.code` 数值一致**。BUG-08（窄屏横向溢出）不在本次范围。

## 2. 变更内容：候选 A（双写）

采用「HTTP status 与 `body.code` 双写且数值一致」，不改动 `{code, message, data}` 结构、不改动 `code` 的取值与语义。本项目的业务码恰好取 200／400／401／403／404／409／500，与 HTTP 状态码一一对应，因此实现上直接取业务码数值作为 HTTP 状态。

### 2.1 全局异常处理：`GlobalExceptionHandler.java`

5 个 `@ExceptionHandler` 原本直接返回 `ApiResponse` POJO（Spring 默认按 200 序列化），改为返回 `ResponseEntity<ApiResponse<T>>`，并抽出唯一出口：

```java
private <T> ResponseEntity<ApiResponse<T>> respond(ApiResponse<T> body) {
    return ResponseEntity.status(body.getCode()).body(body);
}
```

`BusinessException` 的 `code` 是动态的，因此不用 `@ResponseStatus` 写死。409 的 `data.occupiedSlots` 照常回带（FR-10）。

> 计数订正：第 11 周《测试报告》附录写「6 个 `@ExceptionHandler`」，改前按仓库原文数过是 **5 个**（业务异常／参数类／404／方法不支持／兜底）。旧报告已就地注明，不改历史数字。

### 2.2 鉴权拦截器：`AuthInterceptor.java`

- `writeJson()` 原为 `setStatus(SC_OK)`，改为 `setStatus(code)`；手工拼装的 JSON 字符串保持逐字节不变。401／403 在 `preHandle` 里直接写出响应、根本到不了异常处理器，**只改 §2.1 会剩一半的 200**。
- **计划未预见的连锁点（必须记录）**：修复后第一次页面级回归发现，浏览器里所有带 `Authorization` 的跨域请求都被 `net::ERR_FAILED` 挡下，但登录（不带该头）能成功。定位结果是 **CORS 预检也被这个拦截器挡了**：预检响应带着全套 `Access-Control-Allow-*` 头，状态行却是 401；浏览器要求预检为 2xx，于是后续业务请求全部发不出去。修复前 `writeJson` 写的是 200，预检恰好能过，这个隐患一直被掩盖。
  处理方式：`preHandle` 开头放行 `OPTIONS` 预检，交给 Spring MVC 的预检处理器应答；预检不会执行任何 Controller 方法，**不放宽 GET／POST／PUT／DELETE 的鉴权边界**。放行后预检为 `HTTP/1.1 200`，不带令牌的业务 GET 仍为 `HTTP/1.1 401`，取证见 `evidence/curl_options_preflight.txt`。

### 2.3 前端封装：`frontend/src/api/http.ts`

`axios` 默认把 4xx／5xx 判为失败并抛错，会跳过 `then` 分支；若不处理，409 的 `data.occupiedSlots` 会丢失、401 的清令牌逻辑也不会触发。故在 axios 实例上只加一项配置：

```ts
validateStatus: () => true
```

请求入口 `request()`、`ApiBusinessError`、401 `clearToken()`、页面组件（含 `BookingView.vue` 的 `error.code === 409` 分支）**一行未改**。已知取舍：业务失败不再进入 axios 的 error 分支，将来若加全局错误监控，需自行在响应拦截器里处理。

### 2.4 注释口径同步

`ApiResponse.java`（类注释与 `CODE_CONFLICT` 行内注释）、`BookingController.java` 头部、`GlobalExceptionHandler.java`、`AuthInterceptor.java`、`http.ts` 中「业务失败也返回 HTTP 200」一类说法，统一改为双写口径。

### 5.2 六类失败与成功路径：逐条 `status == body.code`

20 条用例实测，**19 条通过、0 条失败、1 条 NOT_TRIGGERED**（「畸形参数触发 500 兜底」的尝试被参数异常处理器接管为 400，未触发兜底；该分支另由 §5.6 实测坐实）。明细见 `evidence/bug07_status_code_regression.json`。

| 码 | 构造方式 | 实测 |
|----|----------|------|
| 200 | 登录、查询会议室、健康检查、正常创建预约 | HTTP 200 ／ `code:200` |
| 400 | 日期参数类型错、结束早于开始、缺参会人数、非法 JSON | HTTP 400 ／ `code:400`，中文提示未退化 |
| 401 | 不带令牌、伪造令牌（**走 AuthInterceptor**） | HTTP 401 ／ `code:401` |
| 403 | 普通用户调 `/api/admin/**`（拦截器）；改他人预约（业务异常） | HTTP 403 ／ `code:403`，两个来源都测到 |
| 404 | 会议室不存在（业务异常）；未匹配路径（NoResourceFoundException） | HTTP 404 ／ `code:404`，两个来源都测到 |
| 409 | 重叠预约 | HTTP 409 ／ `code:409` ＋ `data.occupiedSlots` |
| 500 | 见 §5.6 | HTTP 500 ／ `code:500` ＋ 中性中文提示 |

### 5.3 409 原始报文与 FR-10

`curl -i` 抓到的核心判据（`evidence/curl_409_conflict.txt`）：

```
HTTP/1.1 409
{"code":409,"message":"该会议室在此时间段已被占用",
 "data":{"occupiedSlots":[{"startTime":"10:00","endTime":"11:00"}]}}
```

构造方式：同一未来日期先建 10:00–11:00 与 14:00–15:00 两段占用，再提交 10:30–11:00 的重叠请求；返回的 `occupiedSlots` **只有真正重叠的 10:00–11:00**，不含 14:00–15:00。另测 11:00–12:00 与 10:00–11:00 首尾相接仍可成功（半开区间口径未退化）。

### 5.4 50 并发

`tests/week11/concurrency_50.py` 复跑两次（两个不同的空闲未来日期），两次均为：

- HTTP 分布 **200×1 ＋ 409×49**，逐条 `status == body.code` 不一致 0 条，HTTP 500 **0 条**；
- 业务码 1 成功／49 冲突／0 其他，库内目标时段有效预约 **1 条**，编号去重数＝总数（无撞键）；
- 起跑跨度 5–6 ms（满足「同一秒」）。

证据：`evidence/bug07_concurrency_50_regression.json`。

### 5.5 页面级 / 前端封装层

用无头浏览器加载真实前端，登录后直接调用真实 `src/api/http.ts` 的 `request()`，并调用 `BookingView` 组件自身的提交逻辑：

| 验证点 | 实测结果 |
|--------|----------|
| 登录 → 会议室查询页 | 成功，`localStorage` 有令牌 |
| 409 经 `validateStatus` 后 | 仍抛 `ApiBusinessError`，`code=409`，`data.occupiedSlots=[{10:00,11:00}]` 完整保留 |
| FR-10 页面渲染 | 页面出现「本次冲突的时段 10:00-11:00」，且失败后已填内容保留 |
| 401（令牌置为无效值） | 仍抛 `ApiBusinessError(code=401)`，`clearToken()` 执行，令牌被清空 |
| 刷新后 | 路由守卫把页面弹回 `/login?redirect=/rooms` |

证据：`evidence/bug07_frontend_regression.json`。

### 5.6 500 兜底

畸形参数无法安全触发未预期异常，改用**临时断开数据库 → 请求一个需查库的接口**触发兜底处理器，抓到：

```
HTTP/1.1 500
{"code":500,"message":"服务器内部错误，请查看后端控制台日志","data":null}
```

数据库随后恢复，`/api/health` 回到 `database: UP`。证据：`evidence/curl_500_fallback.txt`。

## 6. 遗留观察项：NF-04 的「即时跳回登录页」

§5.5 实测确认：401 之后 `clearToken()` 会删掉 `localStorage` 的令牌，但**当前页面不会立刻跳登录页**——内存登录态仍在，路由守卫只在导航时执行；刷新或下次导航后才会被弹回登录页。

这是修复前就存在的行为，不是本次状态码改动引入的回归。按本次改动面约束（`http.ts`／注释口径，不引入新的路由守卫机制、不改会话状态实现），**不顺手修**，如实记为遗留观察项：若课程判据要求「401 当刻立即强制退出」，需要单独决策处理方案。
